## ⚠️ 风险评估

### 高风险项

#### 1. 方法间依赖复杂（严重）

**统计**：
- 方法间调用：857 次
- 平均每个方法调用其他方法：7.7 次
- 跨领域调用：频繁

**示例**：
```go
// CreateNetwork 调用了 10+ 个其他方法
func (s *Store) CreateNetwork(...) {
    s.autoSubnetLocked()      // 网络方法
    s.upsertDeviceLocked()    // 设备方法
    s.ensureRelayPort()       // 中继方法
    s.persistNetwork()        // 持久化方法
    s.persistNode()           // 持久化方法
    s.persistTokenByHash()    // 持久化方法
    // ... 更多调用
}
```

**风险**：
- ❌ 拆分后循环依赖风险高
- ❌ 需要大规模重构
- ❌ 可能引入隐蔽 bug

---

#### 2. 测试覆盖不足（高风险）

**现状**：
- 11 个测试文件
- 主要测试 HTTP 端点
- 缺少单元测试覆盖所有方法

**风险**：
- ❌ 拆分后难以验证正确性
- ❌ 可能引入回归问题
- ❌ 需要大量时间补写测试

---

#### 3. 锁使用复杂（中风险）

**现状**：
- 已完成 RWMutex 优化（4个方法使用RLock）
- 65个方法仍使用Lock
- 锁使用分散在各方法中

**风险**：
- ⚠️ 拆分可能破坏锁的一致性
- ⚠️ 需要重新验证所有锁使用
- ⚠️ 可能引入竞态条件

---

#### 4. 持久化逻辑耦合（中风险）

**现状**：
- 持久化方法分散各处
- 数据库事务跨方法
- BoltDB 使用需要一致性

**风险**：
- ⚠️ 拆分可能破坏事务完整性
- ⚠️ 需要重新设计持久化层

---

### 低风险项

- ✅ 只是代码移动
- ✅ Go 编译器会检查一致性

### 替代方案

#### 方案A：渐进式重构（推荐）

**策略**：在新功能开发中逐步拆分

**步骤**：
1. 新增功能时，创建新文件
2. 重构旧功能时，迁移到新文件
3. 每次小规模迁移，验证后提交

**优点**：
- ✅ 低风险
- ✅ 可逐步验证
- ✅ 不影响现有功能

**时间**：分散在多次开发中

---

#### 方案B：优先补充测试

**策略**：先补充单元测试，再拆分

**步骤**：
1. 为Store方法补写单元测试
2. 测试覆盖率达到80%+
3. 再进行拆分

**优点**：
- ✅ 降低拆分风险
- ✅ 提高代码质量
- ✅ 便于未来重构

**时间**：8-12小时

---

#### 方案C：仅提取独立模块（最安全）

**策略**：只提取低依赖的独立模块

**候选**：
- ✅ 授权码模块（8个方法，依赖少）
- ✅ 设备查询模块（部分方法）

**优点**：
- ✅ 风险最低
- ✅ 可验证效果
- ✅ 不影响核心

**时间**：4-6小时
